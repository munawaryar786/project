# Deferred identity-hardening verification gates

**Specifications only. No tests, typecheck, build, audit, provider call, or database command ran during this preparation.** Each gate requires a separately approved implementation and an isolated test environment. Read with [architecture](PHASE3_IDENTITY_HARDENING_DESIGN.md), [email design](EMAIL_VERIFICATION_AND_RECOVERY_DESIGN.md), [phone policy](CANONICAL_PHONE_POLICY.md), and [index rollout](IDENTITY_INDEX_ROLLOUT.md).

| Gate | Future behavior-driven evidence | Environment and release rule |
| --- | --- | --- |
| Synthetic classifier | Explicit synthetic marker required; unknown fields, >2 MiB/10,000 rows, invalid types and conflicting phone candidates reject generically; collisions bucket correctly; groups 1–9 suppressed; no raw input in stdout/stderr; no network/DB module. | Database-free local fixture tests; advisory for design, mandatory before any use. Not run now. |
| Phone parsing | Explicit `+`, `00`, country-context national, SK/CZ/AT/DE/UK/UA/PK cases; malformed plus/letters/extensions/Unicode digits; country-specific plan validity; no forced Slovak interpretation of legacy international values. | Pure unit fixtures with approved parser/version; release-blocking. |
| Phone proof and claim | OTP bound to account/booking and exact canonical key; expiry, retry, single use; two accounts competing for key; phone change rollback on provider or DB failure. | Fake provider plus disposable MongoDB replica set; release-blocking. Provider behavior remains a separate test-mode gate. |
| Verified email enrollment | New and existing accounts, send failure, valid link, expired/replayed link, old versus new attempt, email change, two accounts verifying one key, transaction failure, duplicate-key response, lost inbox. | Disposable MongoDB and fake email sender; release-blocking. Four-language mail content reviewed separately. |
| Reset authority | Only one verified key resolves; unverified/duplicate/unknown/inactive responses indistinguishable; proof tied to identity version; email change versus reset race; atomic password/session/proof outcome; no token in logs. | Disposable MongoDB, fake mail, concurrency; release-blocking. |
| Ambiguous legacy login | Zero/one/many phone and email matches, `take:25` historical search edge, password and OTP paths, invalid phone, no first-record selection, existing sessions retained, safe support outcome. | Synthetic legacy MongoDB fixtures; release-blocking. |
| Registration race and indexes | Concurrent server instances, duplicate canonical phone and verified email, null/missing legacy rows, index build with conflicting data, distributed write gate, duplicate-key mapping, old/new app compatibility. | Disposable replica set with real indexes; release-blocking. Production data never used in tests. |
| Ownership and session | JWT plus live DB session, CSRF, logout, authVersion, legacy upgrade, guest capability, booking continuation, family contact reuse, no contact-based ownership transfer. | Isolated Phase 1/3 regression and browser tests; release-blocking. |
| Multilingual/accessibility | SK/DE/UK/EN enrollment, expired/used/conflict/recovery states, email subject/link language snapshot, generic non-enumerating text, live locale switching, accessible labels/announcements/focus, mobile/screen reader. | Static key parity, browser and human linguistic review; release-blocking for user-facing gaps. |
| Preservation | No payment/Stripe, dispatch/BullMQ, scheduled ride, capacity, luggage, WAV presentation/behavior, M2–M5 email/outbox regression. | Existing isolated suites and source diff review; release-blocking. |
| Staging release | Backup/restore rehearsal, real index inventory, index creation/failure/rollback, two app versions, monitoring and manual exception path. | Separately approved staging; release-blocking. |
| Production release | Approved aggregate audit, human-reviewed collision resolution, final pre-index recheck, explicit change window, rollback operator, observability, owner approval. | Production authorization separate from this task; BLOCKED now. |

Do not use a synthetic fixture result as evidence that real customer identities have no collisions. No automatic account merge, reassignment, deletion or lockout may be added to make tests pass. Phase 4 booking-draft recovery remains a separate authorization and must preserve the account/booking authority boundaries above.
