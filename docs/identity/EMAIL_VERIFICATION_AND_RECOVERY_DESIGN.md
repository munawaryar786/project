# Verified account email and recovery architecture

**Proposal only.** `Passenger.email` is currently populated without an inbox-verification field. It must not be relabeled verified by migration inference. See [policy](PHASE3_IDENTITY_POLICY.md) and [hardening design](PHASE3_IDENTITY_HARDENING_DESIGN.md).

## Proposed identity and proof state

Minimal additive Passenger fields for later approval: `verifiedLoginEmailKey String?`, `verifiedLoginEmailAt DateTime?`, and `emailIdentityVersion Int @default(0)`. Keep `email String?` as legacy/display contact during transition. `Booking.customerEmail` remains separate, optional and non-unique. No persistent account locale is proposed.

Proposed `PassengerEmailVerificationProof` collection: `_id`, `passengerId`, `purpose` (`ENROLL` or `CHANGE`), `proposedEmail` (delivery address), `proposedKey`, `tokenHash` (unique SHA-256 of a cryptographically random 32-byte token), `attemptId` (random opaque identifier), `identityVersion`, `createdAt`, `expiresAt`, `consumedAt`, `cancelledAt`, and optional redacted delivery-status code. PII and token hashes stay in access-restricted database storage; tokens never enter logs, analytics, notifications, booking drafts, or query-visible URLs beyond the existing approved email-link pattern. A dedicated expiring proof model avoids overloading phone-bound `PassengerVerificationProof.normalizedPhone` with email semantics. A pending email need not be stored on Passenger; the proof carries it until verified.

Suggested expiry: 15 minutes, configurable under owner review; only a later tested policy may set a different duration. Expiration must be checked on issue, read and consume, not rely on TTL cleanup. Limit outstanding proofs per account, recipient key and IP. New issuance increments `emailIdentityVersion` and invalidates earlier pending proofs for that account/purpose in the same transaction. Verification requires the matching account, version, attempt ID, token hash, unexpired and unconsumed proof, and the current selected account state. Use conditional update as a compare-and-set; consume the proof and promote the key in one MongoDB transaction. A replay or competing proof can succeed at most once. Delivery happens after transaction commit via existing reliable email infrastructure, with an event identity fixed at issuance and no provider call inside the transaction.

The unique verified-email claim must be enforced by the database. Two accounts may request a proof for one inbox, but only one transaction may promote the same `verifiedLoginEmailKey`; the loser receives a generic outcome and a safe support path. Application prechecks are advisory. Catch duplicate-key conflicts without exposing the other account.

## Enrollment and change sequences

1. **New account:** preserve phone/booking-bound account creation. Treat supplied `Passenger.email` as unverified contact. Once the authenticated account exists, request verification to that inbox; prove control with a single-use link; promote only after the unique-key transaction commits. This must not mint a new booking or change an existing email-event identity.
2. **Existing account enrollment:** require a live database-backed session and CSRF on request. Issue a proof to the proposed address. Until promotion, existing account login by verified phone/password and sessions continue; the email is not a trusted reset destination.
3. **Email replacement:** authenticated request proposes a new address; retain the old verified key until the new inbox is proved. On success, atomically consume proof, claim new key, update `Passenger.email` for compatibility, increment identity/auth version, invalidate outstanding reset/verification proofs tied to the old email, and revoke other sessions according to an owner-approved security policy. The confirming session may be rotated and retained only if account authority was freshly established. A failed send or proof leaves the old verified key untouched.
4. **Competing change attempts:** version fencing makes only the latest issued attempt eligible. An old link cannot overwrite a newer verified address. An account logout or password reset may invalidate pending proofs as part of the security policy, but must be designed and tested with the existing atomic reset transaction.
5. **Password reset after cutover:** resolve only one exact verified key to an active password-enabled account. Always return the same generic public response for none, unverified, duplicate or inactive matches. Issue an account-bound single-use proof to the stored verified destination, not merely the submitted spelling. Complete it through the existing atomic reset path, adding an email-key/version binding so an email changed after issuance cannot authorize a stale proof. Revoking sessions and changing password remain atomic with proof consumption.

## Legacy and lost-access transition

Source confirms `app/api/passenger/password-reset/email/route.ts:30` currently uses case-insensitive `findFirst` on `Passenger.email`; registration and profile updates do not verify that inbox. Existing records therefore have **unknown** email ownership, even if an email is populated. Do not backfill `verifiedLoginEmailAt` from presence, email delivery, or a phone OTP. Maintain existing password/verified-phone login and live sessions while inviting authenticated users to verify an email. For users with no working password, phone or email, use an owner-approved human recovery procedure with independent evidence, not booking-contact matching. The exact transition date and treatment of old unverified email reset requests need explicit owner approval; security recommendation is generic response plus reviewed recovery rather than automated reset to an unverified/ambiguous address. This may reduce automated recovery but must not silently disable existing login or sessions.

Family members can share `Booking.customerEmail` and receive booking communications as already authorized. Only the account's verified email key is exclusive. Never infer `Passenger` ownership from customer, guardian or dispatcher contact email.

## Normalization, interfaces and failure states

The current `normalizePassengerEmail()` uses trim plus whole-string lowercase. Proposed compatibility key: ASCII mailbox syntax and bounded length; trim surrounding whitespace, lowercase the domain and (subject to owner approval after audit) lowercase the ASCII local part to match current case-insensitive login. Preserve dots and plus tags. Do not implement Gmail-specific rules. Unicode local/domain handling and internationalized domain conversion require a separate reviewed policy; reject or hold for support rather than invent a conversion. Audit both raw and current-fold collisions before fixing key semantics.

Reuse existing passenger session/CSRF/rate-limit/email infrastructure. Proposed additive endpoints (names require API review): request verification, complete verification, request change, and inspect verification status. Existing account creation, profile, login and password-reset routes would be adapted later; preserve current HTTP contracts with additive machine-readable codes. The UI must localize request/sent/expired/used/conflict/support states in `sk,de,uk,en` and never reveal account existence. Email links and templates must use M5 recipient locale snapshot and the existing delivery/outbox idempotency. Important wording requires qualified linguistic and accessibility review. Use generic alerts and predictable focus; no forced reload or booking-form reset.

Log only event type, correlation ID and safe result code; never token, key, email, phone, booking reference or raw provider error. Monitor issuance volume, delivery failures, proof completion, expiry, duplicate-key outcomes and human-review cases in aggregate. Unknown provider delivery status is not verification.

## Authorization and verification gates

Schema fields/model, proof expiry, normalization semantics, session-revocation scope, legacy reset transition, support recovery procedure and indexes each need separate owner approval. Test with a disposable MongoDB replica set for concurrent verification, replay, stale version, failed delivery, failed transaction, duplicate key, reset-versus-change race, old sessions, and legacy rows. Verify four-language UI/email and non-enumeration in isolated browser/provider-simulated tests. No such test or provider call was made during this design.
